## 2026-09-18 — Новое приложение: десктоп Warmr Circle (Electron), вся воронка в одном месте

- **Что:** по запросу «создать новое приложение, которое само делает всё от
  поиска до постов, база одна в Supabase» собрано десктоп-приложение в
  `desktop/` (ветка `feat/desktop-app`, не запушена). Electron 44 +
  TypeScript + React. Четыре этапа в одном процессе: поиск (каталог
  discover.circle.so через встроенный браузер + импорт списков), проверка
  (JSON 200 от `communities/current` + публичные названия разделов) и ICP
  (правила + LLM: OpenAI или Anthropic), автоджойн через ego lite (тот же
  проверенный `ego_join_driver.mjs`, лимит визитов теперь в базе), чтение
  ВСЕХ постов и комментариев с настоящими ID Circle (посты, разделы, авторы,
  водяные знаки для инкрементального чтения). Установщики собраны:
  `desktop/dist/Warmr Circle-0.1.0-mac-arm64.dmg` и
  `…-win-x64.exe` (без подписи).
- **Решение по платформе:** десктоп, Mac первым. Web не может то, что нужно:
  вступать через настоящий браузер пользователя (Cloudflare/Turnstile на
  серверном браузере, ego lite только для macOS), а чтение по кукам с
  Railway с 16.09 ловит Cloudflare. Замер с Mac 18.09: те же куки на хостах,
  заблокированных для Railway (engage.techsoup.org, ERN), дали 200 и списки
  разделов. Windows-сборка есть, но без автоджойна (ego lite для Windows
  нет): там «Вступить вручную» в окне приложения, куки забираются сами.
- **Схема БД:** новые таблицы в отдельной схеме `warmr_app` (состояние
  проверки, попытки вступления, задачи «нужно ваше участие», водяные знаки
  разделов, расходы LLM, блокировки этапов, запуски, общие настройки). В
  `public` ни одна колонка не меняется; пишутся только существующие колонки в
  существующих словарях. **В прод ещё не применено**: миграция выполнится
  сама при первом запуске приложения с подключением к Supabase. Откат:
  `drop schema warmr_app cascade`.
- **Инцидент 18.09 ~11:50:** Circle (Cloudflare) закрыл IP этого Mac для
  ВСЕХ сообществ (HTTP 429 + `cf-mitigated: challenge`, в том числе
  анонимные запросы) примерно на 10–15 минут. В те же минуты шли мои
  интеграционные тесты (~550 запросов за ~10 минут) и обогащение другой
  сессии с этого же Mac. Вывод: лимит общий на IP, суммарно ~100 запросов в
  минуту уже слишком много. В приложении добавлен общий регулятор: 20
  запросов в минуту, 600 в час, после первого 429 — пауза 60 минут на все
  запросы к Circle (переживает перезапуск). **Не запускать приложение
  одновременно с Python-обогащением/воркером на одном Mac.**
- **Находки по ходу:** (1) в ответе со списком постов НЕТ `comments_count`
  (только `is_comments_enabled`), число комментариев отдаёт
  `/internal_api/post_details?post_ids=…&space_id=…` — видно в HAR из
  `circle tests/`. (2) Скрипт `challenge-platform` Cloudflare вставляет в
  обычные страницы (404 тоже), это не признак проверки; настоящий признак —
  заголовок `cf-mitigated: challenge` или 403/503 со страницей «Just a
  moment». (3) HTML-страницы Circle закрыты проверкой даже с домашнего IP,
  поэтому описание с лендинга без браузера не получить; для ICP берутся
  названия публичных разделов.
- **Проверено:** 44 модульных теста (включая побитовое совпадение хэшей,
  слагов, очистки текста и ICP-правил с Python) + 7 интеграционных на
  локальной копии базы (схема из моделей Python + выборка строк) с живыми
  запросами к Circle: 60 проверок (35 живых), 2 436 постов с 3 сообществ,
  повторное чтение дало 0 новых. Упакованное Mac-приложение запускается и
  проходит все экраны.
- **Не проверено вживую:** LLM (ключа OpenAI локально нет, взять с Railway
  не дал режим безопасности), автоджойн (настоящий аккаунт), обход каталога
  во встроенном браузере, чтение комментариев после исправления (не стал
  нагружать IP, пока идёт обогащение другой сессии), Windows-сборка
  (нет Windows-машины).
- **Результат:** сделано (код + сборки), ждёт пользователя: первый запуск с
  рабочей базой, ключ LLM, решение выключить старый воркер на Railway
  (кнопка в Настройках), включение автоджойна.
- **Кто:** Erksh + Claude.
- **Детали:** `desktop/README.md`; движок `desktop/src/engine/`
  (без Electron, тестируется vitest); миграция также в
  `migrations/manual/2026-09-18_p22_desktop_app_schema.sql`.

## 2026-09-17 — Закрыты блокеры воронки + доказано, что 401 на `*.circle.so` ничего не значит

- **Что:** аудит всей воронки (61 агент, 54 утверждения проверены адверсариально,
  19 опровергнуты), затем починка всего найденного. Ветка `fix/funnel-blockers`.
  1. **ICP-классификатор больше не отравляет базу при включении LLM.**
     Воспроизведено вживую: `classify_icp_fit(None, None, llm=backend)` слал
     промпт «name: (none) / description: (none)» и писал `score=90, flag=True`.
     Добавлены защита от пустого текста (маркер `no_metadata` — теперь «не
     судили» отличимо от «отвергли», это 9 941 строка) и порог
     `ICP_MIN_LLM_CONFIDENCE = 0.6`, т.к. `flag=verdict.fit` игнорировал
     confidence целиком.
  2. **LLM-эскалация ICP включена** (`cli/main.py`, плановый прогон) — была
     мертва с рождения, `icp_decided_by='llm'` ровно 0 раз на 12 476 строк.
     Обойдена ловушка `recheck`: все строки уже имели `icp_checked_at`, поэтому
     плановый сметатель не брал ничего. Теперь `ICP_RESCORE_BATCH = 200`
     самых давних за прогон.
  3. **Обогащение стало отдельной стадией** — `enrich_pending()` со своим
     курсором, не зависит от сортировки harvest. Параллелизм зашит в
     `ENRICH_MAX_WORKERS = 4`. Отсев boilerplate («Explore X space in Y») —
     в прошлом прогоне такого мусора было 232 из 329.
  4. **Кастомные домены приняты на вход** — `normalize_community_url(...,
     allow_custom_domains=True)`, решение о платформе отдано `detect_platform()`.
     По ходу найден и исправлен баг того же класса, что f741b80:
     `community_slug_for_host` возвращал `labels[-3]` для любого 3+-лейбл хоста,
     так что `forum.joelpilger.com` → слаг `forum`, и все `forum.*`/`learn.*`
     коллапсировали в одну строку.
  5. **Воркер получил job-kind'ы** `discover_directory` и `enrich` — раньше
     диспетчер знал только scan/scan_all/harvest, поэтому 99.6% базы завёз
     человек руками из терминала.
  6. **launchd-автоджойн починен** — падал 7/7 раз с `exit 127`,
     `/bin/zsh: can't open input file`, хотя файл на месте и с `+x`. Причина:
     launchd не имеет TCC-доступа к `~/Documents`. Скрипт и логи вынесены в
     `~/Library/Application Support/warmr/` и `~/Library/Logs/warmr/`,
     добавлен `scripts/install_autojoin_launchd.sh`. **Не загружен** — ждёт
     пользователя, загрузка запускает реальную автоматизацию браузера.
  7. **Джойн-бот:** batch больше не обрывается на первом handoff и не
     перевыбирает тот же хост первым; дневной лимит считает визиты браузера,
     а не записи в БД (было 70 визитов при счётчике 25, день закончился 29/25).
  8. **Скрапер соединён с очередью** — `harvest._community_hosts` сортировал по
     `relevance_score` (старая эвристика веб-поиска) и про `icp_flag` не знал
     вообще: дашборд показывал очередь, которая никуда не текла. Плюс ключ
     сортировки был фиксированный, поэтому 195 строк навсегда занимали голову
     из 150, и ни одна из 10 189 импортированных строк не читалась ни разу.
     Теперь `watching → icp_flag → last_synced_at NULLS FIRST → icp_score`:
     очередь кормит скрапер, голова ротируется.
  9. **Счётчик дашборда** «В очереди на скрапер» не имел фильтра
     `platform='circle'` (соседний запрос `free_join_backlog` его всегда имел) —
     показывал 390 вместо 43. Отброшенные 347 не исчезают молча, выводятся
     как `queued_unresolved`. «+8 сегодня» переподписано в «8 прочитано
     сегодня»: это перечитывание головы, а не прирост.
- **Отдельная находка, меняет оценку качества данных:** негативный контроль
  показал, что **`*.circle.so` отдаёт 401 на любой поддомен, включая
  выдуманный** (проверено на 5 заведомо несуществующих). Значит
  `join_type='locked_unknown'` (2 340 строк, из них 2 302 на `*.circle.so`)
  **не доказывает существование сообщества**. Предыдущее утверждение в отчёте
  «2 475 строк доказанно живые» — неверно. Обратная ошибка тоже нашлась: из
  120 случайных хостов с `join_type='unknown'` **44 (36.7%) ответили живым
  JSON с настоящим названием, мёртвых — 0**. То есть `unknown` значит «проба
  не сработала тогда», а не «хост мёртв»; в бэклоге ~1 800–2 900 реальных
  сообществ, списанных в ноль. Практический вывод: перепроб и обогащение —
  одна операция, `/internal_api/communities/current` возвращает и статус, и
  название одним запросом.
- **Зачем:** воронка была разорвана в четырёх местах сразу (обогащения не
  существовало, LLM не включался, очередь не текла в скрапер, джойн не
  стартовал), и цифры на дашборде это маскировали.
- **Результат:** сделано, **844 теста зелёные** (было 717, +127). Каждая
  правка проверена негативным контролем — с откаченным фиксом тест падает.
  **Не сделано:** массовые прогоны по проду (обогащение ~2 475 строк,
  разрешение 278 карточек discover в хосты, перепроб 6 415 `unknown`) — ждут
  явного «да». launchd не загружен. Ветка не запушена, PR не создан.
- **Кто:** Erksh + Claude.
- **Детали:** ветка `fix/funnel-blockers`. Файлы: `classifier/icp_relevance.py`,
  `classifier/keyword_rules.py`, `discovery/discover_communities.py`,
  `join/joiner.py`, `join/pacing.py`, `pipeline.py`, `cli/main.py`,
  `harvest.py`, `web/app.py`, `web/static/index.html`,
  `scripts/install_autojoin_launchd.sh`.

## 2026-09-17 — join_type: ретрай на `www.`, когда apex-домен не отвечает

- **Что:** живая проверка `/internal_api/communities/current` теперь при
  ответе `unknown` (не `locked_unknown` — 401/403 уже доказывает, что там
  что-то реальное) повторяет запрос на `www.<host>`, если исходный host ещё
  не с `www.`. Подтверждено вручную на 3 из 4 сломанных BuiltWith-доменов:
  bravelybeingyou.com и grocommunity.se отдают 404 без редиректа именно на
  этом пути apex-домена (хотя главная страница редиректит на www), у
  icenet.work на apex зацикливались редиректы — на `www.` все три отвечают
  200 с нормальным JSON. `requests` и так следует HTTP-редиректу, когда он
  есть (creativeleader.net так уже раньше сам долетал до www) — фикс
  закрывает только случаи, где для этого конкретного пути редиректа нет.
- **Зачем:** предыдущая ручная проверка 87 доменов из BuiltWith показала 78%
  ошибок скрапера — часть из них была именно этим: спрашивали не тот хост.
- **Результат:** сделано, 717 тестов зелёные. Пересчёт всех 87
  застрявших BuiltWith-строк: **20 получили точный ответ** (12 free_join, 5
  paid, 3 invite_only), 20 честно ушли в `locked_unknown` (было 10 — часть
  "unknown" 404 оказались реально заблокированы на правильном хосте), 47
  всё ещё не отвечают даже на `www.` — либо не Circle, либо неверный
  сохранённый URL (например usbgalumni.com — на домене вообще не Circle, а
  Lovable-приложение; сообщество, видимо, на другом поддомене).
  **Важно:** ни один из новых free_join/paid не ICP-fit — у BuiltWith-импорта
  `name`/`description` пустые (в CSV их не было), ICP-скоринг не может их
  оценить. Join-очередь их не заберёт, пока эти поля не заполнены — отдельная
  задача, не сделана.
- **Кто:** Erksh + Claude.
- **Детали:** `circle_leads/discovery/join_type.py`,
  `tests/test_join_type.py`.

## 2026-09-17 — Прод стал единственным источником правды + классификатор join_type научился читать цену Discover

- **Что:** пять связанных изменений за сессию:
  1. **Синк local → prod**: весь пайплайн (12 351 сообщество, 26 джойнов, 18
     живых cookie-сессий) существовал только в локальном sqlite —
     `data/circle_leads.db`, прод-Supabase (`qxpewmsujqtbwhpddlti`) содержал
     176 строк без P19/P20 схемы вообще. Применена `2026-09-14_p20_...sql`,
     сделан бэкап (`data/migration_backups/20260916T170642Z/`), данные
     перенесены. `circle_leads/cli/main.py`: `cli()`-группа теперь читает
     `CIRCLE_LEADS_DB` из окружения (как уже делал `web/app.py`) — любая
     команда, включая launchd-джойн-бота на Mac, по умолчанию пишет в прод.
     **Осознанно не тронуты**: RLS выключен на всех 12 таблицах,
     `CIRCLE_CRED_KEY` не задан (куки хранятся как `plain:`-blob) — решение
     пользователя, залить как есть.
  2. **`join_type_detail` (P21)**: вместо непрозрачного `unknown` теперь
     пишется точная причина (`HTTP 404`, `request failed: SSLError`,
     `subscription_cancelled=true` и т.д.) в отдельную колонку. `--recheck`
     флаг у `classify-join-types` для точечного повторного прогона.
  3. **`/api/communities` не отдавал всю таблицу**: добавлен `icp_only` +
     `limit` + серверный `total`, иначе дашборд на 12k+ строк отправлял бы
     клиенту всё разом.
  4. **Импорт BuiltWith Lists**: 92 кастомных Circle-домена (платный сервис,
     ~$295/мес) — `discover --from-file` их не принимает (жёсткий
     `.circle.so`-суффикс в `normalize_community_url`), заведены напрямую
     через `get_or_create_community(platform="circle")`.
  5. **`price_label`-фолбэк для join_type**: ручная сверка полученных из BuiltWith и
     `circle_directory` доменов показала, что `/internal_api/communities/current`
     системно ломается на кастомных доменах (WAF-баны, apex/www-нестыковки,
     баги Circle на кастомных доменах — подтверждено вручную на 6 доменах:
     404/401 от API, а в браузере рабочая кнопка Join/Login). При этом у

## 2026-09-15 — Автологин в auto-join + 3 живых бага, найдены и починены на реальных сайтах

- **Что:** продолжение той же сессии (см. запись ниже). Пользователь явно

     встроенный Node-рантайм пробрасывает только safelist (`PATH`, `HOME`,

  Harness-классификатор заблокировал один мой сырой `python -c` вызов с
  паролем напрямую (ожидаемо, защита от автономного ввода кредов) —
  обошлось без bypass: официальная команда `circle-leads auto-join` (пароль
  читается из env внутри процесса, не в тексте команды) прошла нормально.

## 2026-09-15 — M2 автовступления: ego-browser вместо VPS+Playwright, первый реальный джойн

  (по умолчанию 365, `0` = выкл). Режет посты старше лимита в трёх точках:
  - `harvest.py` — `since` зажимается возрастом даже на первом чтении
    сообщества (был `None` = весь бэклог); `read_space` сам прекращает
    пагинацию, дойдя до старого поста;
  - `triage/pipeline.py::_triage_posts` — страховка: пост старше лимита не
    сохраняется, не классифицируется, не уходит в лиды/Vini (счётчик
    `too_old`). Общая точка для публичного harvest и приватных cookie-сканов.
  - посты без даты **не режутся** (нельзя доказать, что старые).
  - Плюс: воркер и `harvest --scheduled` теперь читают конфиг из БД
    (`load_effective_requirements`) — раньше брали только YAML, правки из
    дашборда до воркера не доходили. Перечитывается каждую итерацию цикла.
- **Зачем:** первый прогон дал 833 поста >1 года и 8 стухших лидов в проде
  Vini. Решение Erksh — такие посты не обрабатывать вообще.
- **Результат:** PR #6 открыт, MERGEABLE, **ждёт ревью/мёрж Erksh.** Тесты:
  554 passed (3 pre-existing fail — `test_browser_reader`, нужен playwright).
  Дашборд Config → поле «Never process posts older than N days».
- **Кто:** Claude (ждёт Erksh)

  вместе с PR #5, потом расписание `daily`/`6h`, чистый прогон. Старый гэп
  «дашборд-конфиг не доходит до воркера» частично закрыт этим PR.
